# 검색·AI 인용 브리프 (사례글용)

지피터스 SEO·GEO 플레이북과 2026-09-18 지피터스 사례글 222편 분석을 사례글에 맞게 줄였다. 스터디 멤버용으로 2026-09-23 7절(한 주 수백 편일 때)을 더했다.

## 0. 데이터가 말한 것 (지피터스 사례글 222편, 2026년 3월부터 9월)

- 발행 5주 지난 165편 중 클릭 100 이상은 21편(13%), 클릭 2 이하는 59편(36%).
- 상위와 하위를 가른 건 본문 구조가 아니라 **제목이 검색어인가**였다. 수치 밀도, 1인칭 비율, 글 길이, 템플릿 사용 여부는 세 그룹이 거의 같았다.
- 제목에 한글+영문 도구명이 있는 비율: 상위 76%, 하위 42%. 제목이 도구명으로 시작하는 비율: 67% 대 37%.
- 상위 글에 실제로 들어온 검색어: "클로드 카드뉴스", "힉스필드 요금제", "omc", "인스타툰 ai", "hermes agent 후기". 제목에 그 단어가 그대로 있다.
- 하위 글 제목: "훔쳐보기", "기억이 사는 집", "3단 배선", "깨달은 것 (1부)". 쓴 사람에게는 재밌지만 아무도 검색창에 치지 않는다.
- AI 답변 엔진 경유 유입이 5건 이상인 글은 7편뿐. 전부 "도구명 + 만들기/가격/연결" 제목에 첫 문장이 정의나 답이었다.

## 1. 제목 규칙

- 검색어(도구명 + 의도)가 앞에, 결과 숫자가 뒤에. 예: "힉스필드(Higgsfield) 요금제 정리: 크레딧 계산과 결제 전 확인 4가지"
- 의도 단어는 여섯 가지 중 하나: 사용법 · 가격/요금제 · 후기/사용기 · 설정/연결 · 비교 · 뜻.
- 발표자 이름 괄호("(OO님 발표를 듣고)"), 행사·기수 머리말("[AI워케이션 2기]"), 시리즈 번호, 나만 아는 별명은 제목에서 빼고 본문으로 내린다. 기수·스터디는 태그가 맡는다.
- 50자 이내. 물음표·느낌표는 1개 이하. 줄표 대신 콜론.

## 2. 리드(첫 150자) 규칙

베터모드는 본문 앞 200자를 메타 설명으로 잘라 쓰고, 발행 후 못 바꾼다.

- 첫 문장은 정의문 또는 답. "힉스필드 요금제는 무료 플랜과 유료 3종으로 나뉩니다."
- 150자 안에 숫자 하나, 검색어 한글+영문 한 번, 확인일(바뀌는 정보일 때).
- 작성자 소개는 여기 두지 않는다. 첫 H2 뒤나 하단.

## 3. AI가 인용하는 것 (연구 2편이 같은 답)

- 숫자·통계 추가: 가시성 +41%. 출처 표기: 하위 페이지에서 +115%. 인용문: +28%. (Princeton·Georgia Tech·IIT Delhi, KDD 2024)
- 게이트키퍼 셋, 없으면 나머지가 무의미: **온토픽**(제목이 약속한 질문에 본문이 답함), **명시적 숫자**, **본문 안 최신 날짜**. (Vishwakarma et al., SIGIR '26)
- 효과 없는 것: 키워드 밀도 맞추기, 쉽게 풀어쓰기만 하기, 분량 늘리기, 포맷만 다듬기.
- 자체 데이터가 제일 세다. 남의 블로그 수치를 옮기지 말고 **직접 잰 숫자**(세션에서 나온 시간·건수·토큰)를 쓴다.

## 4. 작성자 신호

- 작성자 없는 페이지는 AI 인용 확률이 약 40% 낮다. "콘텐츠팀" 같은 익명은 감점.
- 닉네임 + 이 일을 한 입장 + 이 글과의 관련성 한두 줄. 없는 경력을 지어내지 않는다.
- 직함이 아니라 **입장**이다. "동네에서 반찬가게를 하는", "퇴사하고 1인 창업을 준비하는", "AI를 처음 써 보는 초등 교사" 모두 강한 신호다. AI가 보는 건 "이 사람이 이 문제를 직접 겪었나"다.
- 가게 이름·회사명·실명은 필요 없다. 본인이 원할 때만.
- 위치는 첫 H2 뒤 또는 글 하단. 맨 앞에 두면 메타 설명을 잡아먹는다(2026-08-10 실제 사고).

## 5. 한글·영어 병기

같은 도구가 두 표기로 따로 집계된다(프레이머 7,582 / framer 9,642 노출). 한쪽만 쓰면 노출 절반을 버린다.

- 첫 등장에 병기: `힉스필드(Higgsfield)`, `클로드 코드(Claude Code)`.
- 리드·정의문·H2처럼 읽히는 자리에. 본문 아무데나 한 번은 의미 없다.
- 한 문장 안에서 같은 단어를 두 번 병기하지는 않는다.

## 5-1. 지금 사이트(베터모드)에서 되는 것과 안 되는 것 (2026-08 실측)

- 되는 것: 게시글 본문은 서버 렌더라 크롤러가 3,000자 이상 그대로 읽는다. 글 안의 숫자·날짜·작성자·alt는 전부 크롤된다. 개발 요청 없이 글만 잘 쓰면 오늘 바로 노출된다.
- 안 되는 것: JSON-LD 구조화 데이터(벗겨냄), llms.txt(효과 없음), 커스텀 HTML 블록(크롤러가 못 읽음), 표(셀이 붙음). 이런 데 시간 쓰지 않는다.
- 이미지 속 글자는 읽힌다고 가정할 수 없다. 카드·캡처에 넣은 숫자와 도구명은 본문 텍스트에도 쓴다(포털 이전 크롤 스펙에서 확정한 기준).
- 사이트가 날짜를 "3달 전"처럼 상대 표기로 보여주고 마크업도 비표준이라, **본문 안 절대 날짜**가 AI에겐 유일한 날짜 신호다.
- 도구 뉴스는 많은데 "AI 툴 추천" 질문에서 인용이 0건이었다. 개별 도구 글은 인용되므로, 사례글은 **한 도구를 깊게** 쓰는 쪽이 맞고 취합·비교는 별도 글의 몫이다.

## 6. 검색어 조사 (스킬이 한다, 멤버에게 묻지 않는다)

1. DEVLOG의 도구명·기능명을 한글·영문으로 뽑는다.
2. `site:gpters.org 도구명 업무` 로 이미 있는 글을 확인한다(7절). 같은 의도의 글이 있으면 이번 글은 다른 의도(예: 사용법 대신 설정, 후기 대신 비교)로 튼다.
3. `도구명 사용법`, `도구명 후기`, `도구명 설정` 같은 조합을 검색해 상위 글 제목 패턴을 본다.
4. 제목 후보 3개를 만든다. 검색어 앞 + 구체적 대상 + 결과 숫자 뒤(7절). 멤버는 고르기만 한다.
5. 어느 조합도 검색 결과에 관련 글이 거의 없으면 "검색 수요가 안 잡혀요"라고 말하고 rules.md 6절(도구로 다시 잡기 → 기록형)로 간다.
6. 검색 도구가 없는 환경(웹 검색이 꺼진 코덱스 등)이면 2·3단계를 건너뛰고 1절·7절 공식만으로 제목을 만든 뒤 "검색 확인은 못 했어요"라고 알린다.

## 7. 한 주에 수백 편이 올라올 때 (스터디 기간)

스터디 기간에는 이 스킬로 한 주 200~300편이 올라온다. 한 편만 보면 맞는 규칙도 수백 편이 같이 따르면 서로를 깎는다.

**제목끼리 겹치지 않게**

- "클로드 코드(Claude Code) 사용법"처럼 도구명 + 의도만으로 끝나는 제목은 한 주에 수십 개가 나온다. 구글은 같은 사이트의 비슷한 글 중 하나만 보여준다. 나머지는 묻힌다.
- 제목 공식: **도구명(한영) + 구체적 대상·업무 + 의도 + 결과 숫자.** 대상·업무가 제목을 가른다.
  - ❌ "클로드 코드 사용법: 업무 자동화 후기"
  - ⭕ "클로드 코드로 세금계산서 엑셀 정리 자동화: 40분에서 3분으로"
  - ⭕ "챗GPT(ChatGPT)로 반찬가게 인스타 문구 한 달 치 만들기: 30개를 2시간에"
- 대상·업무 단어는 멤버의 입장(프로필)과 DEVLOG에서 가져온다. 업종·대상이 들어가면 자연스럽게 겹치지 않는다.
- `site:gpters.org 도구명 업무`에서 **같은 도구 + 같은 업무** 글이 이미 있으면, 의도(설정·비교·가격·후기)나 대상(업종·규모)을 틀어 다른 질문에 답하게 한다.

**틀 흔적이 남지 않게**

- 모든 글이 "📝 한줄 요약 / 🎯 이런 분들께 도움돼요 / 😫 문제 상황"으로 시작하면 수백 편이 같은 뼈대가 된다. 검색엔진은 틀로 찍어낸 글을 대량 생성 콘텐츠로 보고 사이트 전체를 낮출 수 있다.
- 그래서 **소제목은 틀에서 가져오지 않고 그 글의 내용으로 쓴다.** 독자가 검색할 질문이나 그 섹션의 결론이 소제목이 된다. "세금계산서 파일명이 제각각일 때 어떻게 묶었나", "40분이 3분이 된 이유".
- 구성(스토리텔링·비교·튜토리얼·짧은 후기)은 글 내용에 맞춰 고른다. 늘 같은 구성을 쓰지 않는다.
- 글마다 다른 것: 직접 잰 숫자, 실제 캡처, 막힌 지점, 멤버의 입장. 이 넷이 있으면 틀이 비슷해도 다른 글이다. 넷 다 없으면 쓰지 않는 게 낫다.
